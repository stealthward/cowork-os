# AI Workforce

## Project Identity

Build the agent workforce that runs Brett's own work, top-down: three executive seats directly under Brett (chief of staff, COO, CMO; Brett, 2026-09-25), each a brief the session wears because a seat has to talk to Brett and dispatch workers, and each with its own subagent specialists built underneath it. Document the architecture well enough that the same build can be repeated for each team member once Team Edition is in place. This project belongs to the Operations workstation. Until Team Edition, nothing is built for another user (Brett, 2026-09-23): every agent, skill, and rule serves Brett, and the team phase starts from the pattern this project proves. End state for this phase: Brett runs his work through agents and skills he can see, manage, and improve from one page, with the model and cost rules behind them written down, and a build method a second person could follow. This folder is the workshop: plans, course notes, comparisons, the systems registry, and decisions live here. Anything that runs (agent files, skills, settings, hooks) lives in `.claude/` at the Cowork OS root, because that is what the Code tab reads. External tracker: the [AI Workforce project in Asana](https://app.asana.com/1/459051476492004/project/1218848903060628) (build tasks by seat, created 2026-09-24, re-planned 2026-09-28); BW AI was folded in and archived 2026-09-28; courses sit in Brett's World Queue as team resources. Brett's priority order lives in Brett's World in Asana; check it before proposing lane order.

## Workflow

1. Read MEMORY.md in this folder for the current phase and open items, then roadmap.md for the plan and the gate you are working toward.
2. Before building any agent or skill, read model-selection.md and pick the model by its rules. Log the choice in systems-registry.md.
3. When Brett shares a course, create one intake file in courses/ from the template, then update courses/comparison.md. Summarize in your own words, but keep the source's framework names, step labels, and coined terms exact and every component in order; quote short key phrases with a citation, never long passages.
4. Build on the Code tab in the desktop app. Cowork tab sessions cannot read agent files (see 00_Resources/cowork-vs-code.md).
5. Any new agent, skill, scheduled task, app Project, or satellite gets a row in systems-registry.md in the same session it is created. No exceptions. The row carries a description, connected platforms, and for a seat or worker its Reports to; a scheduled task also gets its cadence in registry-page/links.json. Then run registry-page/render.py and republish the page in the same session.
6. Phase boundaries in roadmap.md are Brett approval gates. Finish the gate, show the evidence, wait.
6a. Gates are milestones and events, never dates (Brett, 2026-09-25). A seat, worker, or phase is built when the thing it depends on exists, and it gets real tasks the moment its brief is approved. Never write "two weeks" or a calendar deadline into a brief, eval, or plan; write the evidence that unlocks the next step. Brett's time is going to this build, so speed to a real task is the priority. Refined 2026-09-28 (Brett): Asana tasks carry target due dates, calculated backward from Brett's targets and set on his approval, so the day plan can schedule them; a gate still passes only on evidence, and a missed target becomes a question, not a pass. Briefs and evals stay free of calendar deadlines.
7. End every working session with "audit this session" so decisions reach MEMORY.md.
8. Close every thread in this project with these, in this order (Brett, 2026-09-24): a recommended stopping point (why here is a clean break); a recap of what was accomplished, with every file created or changed; and a next step only when this thread's own work leaves something unfinished that is not already an Asana task. Write that next step as one sentence Brett can paste as the opener, and make it a task before the thread closes. Otherwise give no next step: never a step unrelated to this thread, and never a pointer to tasks Brett already follows in Asana (Brett, 2026-10-12). Then the Thread Close list in root CLAUDE.md; a finished Session Plan entry is deleted, not archived, since history lives in the seat logs (Brett, 2026-10-14). Never recommend a stopping point while a deliverable (an agent file, an eval, a plan) is still waiting for Brett's review; his feedback is the likely next step, so hand over the files, wait, and close only after he has reviewed them (Brett, 2026-09-25).
9. Work that spans more than one thread is tracked as Asana tasks in the AI Workforce project, not as bullet lists in chat (Brett, 2026-09-24). When a next step is named in a closing recap, it already exists as a task.

## Project Rules

- Tag every artifact Shared Core or Personal Layer when it is created. Shared Core never references Max Income, compensation, ownership percentages, or personal matters (apriliapeace, 2212 Issues).
- Nothing is built for a team member until Team Edition is in place, and nothing gets shared until the Shared Core and Personal Layer are physically separated in the team kit (team-kit/ until 11/10, then the Claude-synced GitHub repo). Team-facing work that already exists is parked in `parked/`, not deleted.
- When a Shared Core file changes, the COO updates its team-kit/ copy in the same session, applying the same scrub, and reruns the leak check on that file. A new file in .claude/ or 00_Resources/ gets classified before the kit is copied for anyone. (Brett, 2026-10-30)
- Every recommendation taken from a course or an expert is presented with pros and cons for Brett's businesses and a clear recommend or not. Brett has not taken every course, so never assume he has the context; name the source and the lesson.
- Course recommendations are compared before they are adopted. Adoption decisions go in MEMORY.md under Key Decisions with the reason and the course that drove it.
- Cheapest model that passes the check wins. Do not put Opus or Fable on a task because it feels important; put it there because a cheaper model failed the eval or the cost of a wrong answer is high (money, legal, client-facing).
- Organization before dashboard. A dashboard over an unregistered system is a prettier mess. The registry on disk is the source of truth; any dashboard renders from it.
- Brett does not hand-edit agent files, settings, or hooks. Give exact click-paths for anything done in the desktop app.
- When a core context document is written or materially changed (brett-profile.md, audience-personas.md, growth-strategy.md, initiatives.md, voice-principles.md), hand Brett the changed sections for a quick nuance review before any agent or eval depends on them. He catches what the files get subtly wrong. (Brett, 2026-09-24)
